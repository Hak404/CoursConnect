## Important Details
- Contraintes utilisateur : pas de modification inutile du frontend validé ; ne pas réécrire l'architecture existante ; pas de fonctionnalités fictives ; étape par étape ; recompiler après chaque correction ; distinguer problème d'environnement vs problème de code.
- **Décision utilisateur : WildFly sur hôte 8081** (le 8080 = conteneur `tomcat_server` Cabinet_Medical — ne pas toucher ; Postgres 5432 = autre projet).
- **Encodage UTF-8 — cause racine trouvée et corrigée** : (1) données DB double-encodées en mojibake (`MathÃ©matiques`) importées via un client corrompu — réparées par `CONVERT(CAST(CONVERT(col USING latin1) AS BINARY) USING utf8mb4)` (colonnes pure mojibake) + UPDATEs manuels (notifications ids 1-7/11-16, reviews 1/2/4) via `backend/repair-utf8.sql` ; (2) connexion JDBC en latin1 → les écritures app corrompaient — datasource URL passée à `...?useSSL=false&serverTimezone=UTC&useUnicode=true&characterEncoding=UTF-8` (appliquée via `backend/ds-fix.cli` + `:reload`). Tables en utf8mb4. Vérifié : écriture/lecture accents propres (ex. réservation étudiant → colonne `meeting_location` propre en base).
- **Paiement & lieu — règles métier (backend autoritaire)** : nouveaux enums `PaymentMethod` (CASH/ONLINE) + `PaymentStatus` (UNPAID/PENDING/PAID/FAILED/REFUNDED) ; **seul CASH est accepté à la création** (ONLINE → ConflictException 409 « Paiement en ligne — bientôt disponible ») ; **montant = (negotiatedPrice ?? price) × durationMinutes / 60** arrondi HALF_UP 2 déc., devise `DH`, recalculé par le backend même pour les anciennes lignes (`amountOf` fallback) ; `UNPAID` à la création, `markPaid` (professeur) uniquement si **COMPLETED** → `PAID` + `paidAt`. **Lieu privé** : `meetingLocation`/`meetingLink` exposés dans le DTO **uniquement si statut ACCEPTED ou COMPLETED** (rien sur les fiches publiques — vérifié aucune fuite). Logique par `LocationType` : STUDENT_HOME/OTHER → adresse requise à la création (409 si absente) ; PROFESSOR_HOME → snapshot `professors.teaching_address` (surchargable à l'acceptation) ; ONLINE → `meetingLink` fourni par le professeur à l'acceptation. `BookingAcceptDTO` (meetingLink + meetingLocation) ; endpoint `PUT /bookings/{id}/payment/mark-paid`.
- `ApplicationConfig.getClasses()` non vide ⇒ pas d'auto-scan : tout nouveau `@Provider`/filtre doit être ajouté à `getClasses()`.
- **Hibernate 6 garde les noms verbatim** → `hibernate.physical_naming_strategy=CamelCaseToUnderscoresNamingStrategy` dans persistence.xml (élimine les WARN "add column" au déploiement).
- **Échecs de login → 500 (bug #?)** : les exceptions lancées dans un EJB `@Stateless` (`AuthService.login`) sont enveloppées par l'EJB container en `jakarta.ejb.EJBException`, et `GlobalExceptionMapper` (ExceptionMapper<Throwable>) tombait sur le cas par défaut 500. Correctif : les 4 classes `com.coursconnect.exception.*` annotées `@ApplicationException(rollback = false)` → propagées sans wrapper. **Vérifié : login inconnu/mauvais mdp → 401.**
- `@Context ContainerRequestContext` en paramètre de méthode → `RESTEASY003880` (proxy Weld/RestEasy 6.2) → 500 sur tous les endpoints protégés. Correctif retenu : **helper `CurrentUserHolder`** (`@RequestScoped`, champ `User`) injecté (`@Inject`) et rempli par `AuthFilter` à l'auth ; ressources lisent `requireRole(currentUser, Role)` / `requireAuth(currentUser)` ; lecture du header token : `@HeaderParam("Authorization")` (plus aucun `@Context` dans les ressources — vérifié, reste uniquement dans les signatures de filtres `CorsFilter`/`AuthFilter` qui sont normales).
